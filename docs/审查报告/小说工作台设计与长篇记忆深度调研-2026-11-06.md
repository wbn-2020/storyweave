# 小说工作台设计与长篇记忆深度调研

日期：2026-11-06。对象：织章 · StoryWeave 当前工作树。重点：零经验作者的功能需求，其次为长篇记忆、架构可靠性、技术成本与 UI。

**结论：产品方向值得保留，现有源码并不只是一个知识库；最大的不足，是还没有把已有能力组织成新手可以连续完成的创作流程。** 建议优先补齐“故事种子 → 章场规划 → 粗稿 → 有目的的改稿 → 版本对照 → 定稿与交付”，同时补好人物历史时点、摘要可信度和完整恢复。增加上下文长度、角色卡数量或图谱复杂度，不能替代这些工作。

本报告是研究与设计评审，不是已经批准的实施方案。建议优先级不改变现有开发范围；明确待开发的事项不作为突然发现的缺陷。本文未启动项目、原型或服务，未安装依赖，未运行测试、SQL、模型请求、类型检查、编译、构建或打包，也未新增单元测试。

阅读建议：先读第 1、3、4、5 节理解产品功能；第 6、7 节解释记忆与架构；第 8、9 节给出界面和推进建议；第 10 节是将来获得授权后才执行的验收场景。

## 1. 总体判断：已有的东西与最值得补的东西

### 1.1 已经做对的方向

1. **低门槛开始。** 建书建章只需名称，不强制先填完整大纲、人物传记、世界观或连接 AI。源码中的低门槛，应在界面文案上继续强化。
2. **作者控制采用。** AI 规划、正文、知识候选与最终定稿分开；生成不是自动覆盖。固定输入、版本冲突和作者决定都有对应结构。
3. **正文是可追溯资产。** 保存形成不可变版本，恢复旧稿产生新的工作稿，作者定稿有独立指针。
4. **没有把所有记忆都包装成真相。** 作者设定、未来计划、正文陈述、人物认知、AI 整理、AI 推断、外部参考分别记录；“已采用”“来源可查”“没有待处理冲突”也没有被直接等同于客观事实。
5. **技术路线符合个人机。** Electron、受限 preload、独立业务进程、每书 SQLite、分批任务和本地检索，比默认要求服务器、图数据库或本地大模型更合适。
6. **已有可解释上下文的基础。** 能预览实际 messages、接口、版本、所选资料、预算及警告，而不是只显示一个“AI 已记住全书”的按钮。

这些都是源码或设计结构上的正面证据，不表示已经通过运行验收。

### 1.2 优先级最高的改进方向

| 优先方向 | 为什么重要 | 本轮结论性质 |
|---|---|---|
| 新手第一章引导 | 不知道写什么的人，不能只得到“建立章节” | 产品机会；现有入口范围已核对 |
| 场景规划与规划采用 | 长备注不等于可执行的下一场 | 采用为备注已确认；场景闭环属于设计补齐 |
| 分层改稿指导 | “改写一下”不能教作者判断结构、人物或语言的问题 | 产品机会，未证明实际用户必然受阻 |
| 抽取时关联已有实体 | 长篇中人物反复出现，新条目不应代替身份消歧 | 当前新建路径已确认；建议新增作者选择 |
| 人物历史状态与知情 | 倒叙、误解修正、隐瞒不能只靠当前人物卡 | 当前时点范围边界已独立复核 |
| 摘要逐项有据 | 引文存在不证明整段归纳都正确 | 质量边界已独立复核，非已观察幻觉 |
| 版本对照、来源定位、作者改稿留存 | 改稿需要看清变化，也需要能暂时离开 | 界面范围与产品机会 |
| 完整恢复包 | 正文导出、数据库升级副本都不等于完整作品恢复 | 已明确在 D6 计划内，正式交付前必须完成 |

**不是建议推翻现有底座，也不是建议立即扩张成全自动写书系统。** 功能完善应优先复用现有章节字段、版本、出处、采用记录与任务结构。

### 2.2 什么叫“有问题”

- **已确认范围／静态确认**：实际字段、分支或调用链支持该结论。例如“规划采用为备注”。不代表用户体验失败或故障已经复现。
- **改进机会**：当前实现不一定错误，但可更符合目标用户。例如首章三问、版本命名。
- **明确待开发**：当前进度已列出的工作，如 D6 完整恢复包。不重复包装为新发现。
- **待验证**：需要真实输入、模型、数据库或界面行为才能下结论。不得写成“已经卡顿”“已经丢稿”“保证不剧透”。

本轮分为功能、新手概念、记忆、架构、UI 五条调查线，另外两条独立复核线核对核心命题。复核结论及未覆盖范围见第 11 节。论文结论只用于说明机制和评估方法，不用于推断本项目、中文小说或某个当前模型已达到论文成绩。

## 3. 不需要先学一堆术语：这些概念到底是什么

以下例子均为原创。术语在不同社区并不完全统一，产品应该首先使用易懂中文。

| 概念 | 通俗解释与例子 | 在织章里怎样用 |
|---|---|---|
| 拆书 | 看一部作品怎样安排目标、冲突、信息、转折和章节作用。例如“先发现铜灯失踪，再让证词互相冲突” | 叫“写作参考分析”；分析手法，不是换词复制剧情 |
| 角色蒸馏 | 社区常用来指提炼人物的欲望、性格、表达习惯。例如“阿禾嘴硬，却主动替朋友偿债” | 叫“整理人物特点”；不是每位作者必做的步骤，也不是统一技术规范 |
| 模型知识蒸馏 | 机器学习中把较大模型或集成模型的知识压缩到另一模型，通常涉及训练〔G03〕 | 与整理人物资料不同；本项目不需要为了角色档案训练模型 |
| 角色卡 | 可保存、交换的人物描述。包含性格、背景、口吻，有的格式还带聊天提示和示例对话 | 用户界面优先叫“人物档案”；不等于人物此时全部状态 |
| 世界书／Lorebook | 条件满足时把资料带入提示的条目集合。例如提到“雾桥”时带入夜间禁行规则 | 借用“按需带入资料”的思想；它不是自动可靠的真相库 |
| Story Bible／创作契约 | 作者记录作品方向、人物、世界规则、文风和边界。例如“现实悬疑，不用超能力解案” | 叫“作品设定／写作约定”；不是法律合同，也不必一次填完 |
| Codex | 部分写作工具给集中作品资料目录起的名称 | 叫“作品资料”；不是统一格式或记忆算法 |
| 场景 | 一段相对完整的行动或体验。例如“阿禾在码头追问铜灯去向” | 可问：人物想做什么、受什么阻碍、结束后有什么变化 |
| 章节 | 作品的阅读与组织单位，一章可以包含一场或多场 | 章和场不要混用；分场不必强制 |
| 情节节拍／Beat | 某个重要变化或动作。例如“证人改口”“阿禾决定跟踪” | 叫“剧情要点”；不需要先学某套结构公式 |
| 设定与已发生事件 | “阿禾会开锁”是设定；“昨夜阿禾打开仓门”是事件 | 两者都需要来源或作者决定，但使用范围不同 |
| 人物认知与读者已知 | 阿禾相信铜灯被偷，读者却看到铜灯被藏；故事真相还可能是第三种情况 | 三者分别维护，不由参与、提及或作者采用自动推导 |
| 章节／全书摘要 | 对已写内容的压缩，例如“铜灯失踪，阿禾开始怀疑证词” | 帮助回忆经历；可能漏细节，不能替代原稿证据 |
| RAG／检索增强 | 先找到相关资料，再交给 AI 协作 | 用户看到“本场资料／查找相关资料”即可；不是训练 AI |
| 长上下文 | 一次请求能放更多文字 | 只是输入容量，不等于正确记住所有人物、时间和修订 |

### 3.1 角色聊天与小说创作不是同一个问题

角色聊天工具主要回答“这个人物下一轮如何回应”。长篇小说还要组织场景、叙述顺序、事件因果、读者揭示、人物知情、草稿与定稿、修订影响和交付资产。

SillyTavern 的角色卡、世界书、Data Bank 和聊天向量化值得参考〔C01–C04〕，但不能直接替代小说记忆模型。把一大张角色卡长期塞进上下文，仍无法回答“第一章的阿禾是否已经知道第五章才揭示的秘密”。

### 3.2 拆书的边界

只处理自写、授权或依法可以使用的资料；不把未经许可的商业小说批量抓取、转换为仿写库。一个有价值的输出应分成：**观察到的结构技巧、原文证据、可以尝试的原创练习**，而不是“复制人物、换名、重写句子”。

参考作品的人物和事件不属于自己的作品正史。使用参考时仍需说明内容是否会送到外部模型；不承诺版权、平台规则或出版结论。此处是产品与安全建议，不是法律意见。

## 4. 同类产品给出的启发与功能覆盖

### 4.1 哪些设计值得借鉴

| 对照对象 | 本轮实际读到的能力／流程 | 对织章的启发 | 不应直接推导 |
|---|---|---|---|
| Novelcrafter〔P01–P04〕 | 章场组织、大纲落地、Codex、场景生成与采用 | 规划成果需要进入可继续操作的章场；资料是协作输入，不应喧宾夺主 | 有 Codex 不等于自动消歧、无矛盾或防剧透 |
| Sudowrite〔P05–P07〕 | Story Bible、章概要→场景→草稿、明确意图的改写 | 给不熟悉写作的人问题、示例与可调整步骤；生成前知道要改变什么 | 故事引擎不保证文学质量，也不应强制全部走 AI |
| Scrivener〔P08–P09〕 | 空白与章场模板、Binder 组织、快照、编译；部分证据来自官方作者访谈 | 手工写作、研究资料、版本和交付仍是工作台的基本价值 | 作者访谈不是功能测试或效率基准 |
| SillyTavern〔C01–C06〕 | 人物格式、条件世界书、资料作用域、聊天召回 | 借鉴交换格式与资料作用域，不照搬聊天状态语义 | 角色卡格式、自动注入或向量化不保证长篇正史正确 |
| 场景工艺资料〔P10〕 | 目标—冲突—结果，以及反应—困境—决定等思路 | 作为可选提问和改稿检查，而不是评分公式 | 所有小说必须套相同结构 |

### 4.2 当前功能矩阵

“源码覆盖”只表示本轮看到了静态实现或链路；“未找到证据”不等于在所有文件或未来计划中确定没有。

| 功能 | 当前证据 | 主要判断 |
|---|---|---|
| 建书、作品资料、归档 | 源码覆盖 | 起步只需名称，类型与简介可后补 |
| 从模糊想法到第一章的引导 | 所读入口未找到完整引导 | 值得优先增加可跳过的脚手架 |
| 全书文风、创作边界约定 | v4 已有设计；正式资料较轻 | 不要让重要约定只散落在要求和备注中 |
| 卷章创建、重排、筛选 | 源码覆盖 | 长篇组织已有基础 |
| 本章目标、视角、字数、备注 | 源码覆盖 | 已有轻量规划，不是“没有大纲” |
| 独立场景的计划、位置和移动 | v4 有设计；正式编辑器有分场线 | 分场标记不等于稳定场景工作单元 |
| 场景目标、阻力、转折提示 | 所读入口未找到完整引导 | 新手比熟练作者更需要问题与例子 |
| 人物长期特点、地点、物品、规则 | 源码覆盖 | 使用知识条目承载，详细档案可渐进填写 |
| 关系、事件、伏笔、人物认知 | 源码覆盖 | 已有显式结构和历史，不应再报为全缺 |
| 人物形成时点、可叠加读者披露 | 新源码已接线 | 限制附加认知资料，不是完整历史心智 |
| 任意时点完整人物状态还原 | 尚未完整覆盖 | 形成时间、状态变化与历史有效期需整合 |
| 正文编辑、分场、专注、查找替换 | 源码覆盖 | 实际 IME、撤销和长章体验未运行验证 |
| AI 章节规划 | 源码覆盖 | 采用追加到章节备注 |
| AI 续写、连续段落改写、作者采用 | 源码覆盖 | 有局部协作闭环，不自动定稿 |
| 有理由的结构／人物／语言改稿指导 | 所读入口未找到完整指导流程 | 可先复用现有改写和人工清单 |
| 章节摘要、知识提议审阅 | 源码覆盖 | 全部引文保留；知识采用当前为新建条目路径 |
| 逐章任务、卷／全书分层汇总 | 源码覆盖 | 固定完整来源，不静默截断；质量未验收 |
| 关键词、名称别名、显式实体检索 | 源码覆盖 | 不等于全文自动实体解析 |
| 向量与混合检索 | 源码覆盖 | 有限扫描、排名融合；召回效果未验收 |
| 创作前自动推荐本场资料 | 当前主要手选 | 可先推荐并说明理由，不自动放行所有资料 |
| 自动关系／事件／认知维护 | 自动整合明确待开发 | 新知识条目不是结构化故事状态自动更新 |
| 记忆／图谱／时间线可视化 | v4 有设计；D6 明确待开发 | 应服务具体查询与正文定位，而非装饰性星海 |
| 写作参考、灵感与方法 | 外部参考性质已有；专门流程未找到，相关能力有后续计划 | 拆书不是首章前置任务 |
| 通用角色卡／世界书交换 | 未找到正式通用导入 | 可选，先资料映射，不承诺执行兼容 |
| TXT／Markdown 导入导出 | 源码覆盖 | 正文交换不携带全部恢复资产 |
| DOCX／PDF 等更多输入 | 本轮未确认正式链路 | 不自动变成首期必需；先明确授权、转换与校对成本 |
| 历史阅读、恢复、独立定稿 | 源码覆盖 | 可恢复基础正确，实际恢复未运行 |
| 命名检查点、两稿差异 | v4 有目标；正式历史页为单稿预览 | 提高改稿可解释性，避免同时载入许多长稿 |
| 生成原提议与作者本地改稿 | 原提议可持久留存，未采用修改有离开门禁 | 作者改稿稍后处理仍需完善出口 |
| 定稿前检查与导出清单 | 范围选择已有，按章清单可补 | 已明确会跳过未定稿章节，不是静默漏章 |
| 单章草稿留存与数据库升级副本 | 源码覆盖 | 与完整作品恢复包是三种不同能力 |
| 完整作品恢复包 | D6 明确待开发 | 正式交付前的重要条件 |
| 提供商兼容、成本、资源与质量验收 | 部分契约已有；真实行为待验证 | 参数存在不能替代兼容或质量证据 |

## 5. 功能方面的详细建议：先让作者知道下一步

### DR-01｜高｜改进机会：第一章入口需要帮助开始故事

**场景与证据：** 创建作品后，空态标题为“从第一场开始”，实际按钮仍是建立章节；本章资料仅问“这一章要推进什么”。见 [App.tsx:633](../../src/renderer/App.tsx#L633)、[EditingDialogs.tsx:41–45](../../src/renderer/components/EditingDialogs.tsx#L41)。

**建议：** 提供可跳过的三问：“谁想得到什么？受到什么阻碍？章末发生什么变化？”给一段原创短例子，回答直接进入已有目标／备注。允许暂名，也允许不回答直接写。〔P05、P10、U04〕

**代价与边界：** 低，主要是内容设计。不要强制建人物库、填世界观或使用 AI。独立复核确认了入口范围，但没有证明真实新手一定卡住。

**将来人工验收：** 没有稿件、设定、模型配置的人，从书架开始即可写出粗稿；能说明提示可跳过。

### DR-02｜高｜设计补齐：章和场应该成为可理解的两个层次

**场景与证据：** 一章含“码头追问”和“回家核对证词”两场，目标、地点和视角可能不同。正式章节结构有目标、视角、备注，编辑器提供分场线；v4 才表达独立场景操作。见 [api.ts:53–77](../../src/contracts/api.ts#L53)、[ManuscriptEditor.tsx:130–139](../../src/renderer/components/ManuscriptEditor.tsx#L130)、[v4 说明:19–24](../../design/ui-v4/README.md#L19)。

**建议：** 先建立可选“本章场景清单”：每场一个名字、目标、阻力、结束变化，能够定位正文。第一阶段可与现有分场线配合；如果要跨章移动、绑定时点和稳定出处，再明确场景身份及编辑锚点的契约。〔P01、P06、P09〕

**代价与边界：** 轻量清单为中低，稳定场景移动为中。不能只改 UI 名称就宣称场景对象已实现；也不能要求所有章节都分场。独立复核未覆盖编辑器完整场景链路，该整体建议保留为设计补齐。

### DR-03｜高｜采用范围已确认：规划应能转成可执行的下一步

**证据：** 当前规划采用追加 `notes`，并不会填入本章目标或场景清单；这与界面“采用为章节备注”一致。见 [ai-repository.ts:471–474](../../src/infrastructure/ai/ai-repository.ts#L471)、[AiPanel.tsx:827–829](../../src/renderer/components/AiPanel.tsx#L827)。

**建议：** 允许作者选择计划中的某一项，明确采用到目标或场景计划，再“开始写这一场”。保留自由文本入口；已有目标不自动覆盖，未写出的计划不进入已发生事件。〔P02、P06〕

**代价与边界：** 中低，可复用现有采用、版本与字段。不建议一次把模型大纲自动展开为整本事实。静态独立复核确认“追加备注”，没有否认已有规划能力。

### DR-04｜高｜改进机会：从“改写”升级为有目的的改稿

**场景与证据：** 新手觉得“读起来平”，却不知道应改因果、人物动机还是句子。任务已有规划、续写、改写、摘要和抽取，但要求主要由作者自行填写。见 [AiPanel.tsx:45](../../src/renderer/components/AiPanel.tsx#L45)、[AiPanel.tsx:786–787](../../src/renderer/components/AiPanel.tsx#L786)。

**建议：** 三类可选入口：结构与因果、人物与视角、语言与对话。每次指出一处原文、一个理由和一项小改动，先让作者判断，再调用现有改写。例如“这个场景结束后是否改变了下一步行动”，而不是给“文学性 87 分”。〔P07、P10〕

**代价与边界：** 人工清单为低，带出处的模型建议为中。不要承诺自动文学评判；也不应把某套场景公式变为强制检查。

### DR-05｜中｜产品机会：作品约定需要轻量、可更新的固定位置

**证据：** 正式作品资料主要是名称、类型和简介，章节另有目标、视角和备注；v4 有创作契约设计。见 [EditingDialogs.tsx:21–45](../../src/renderer/components/EditingDialogs.tsx#L21)、[v4 说明:24](../../design/ui-v4/README.md#L24)。

**建议：** 可选记录一句话故事、主角欲望、叙事视角原则、文风和不可违反的边界。例如“现实悬疑，不用超能力解决案件”。按任务选入并展示实际发送范围；约定修改也要有版本与影响提示。〔P03、P05〕

**代价与边界：** 中低。不要建设几十个必填字段，不能仅因新版 PRD 缺失认定当前已决定的功能范围不含这些能力。

### DR-06｜中｜产品机会：人物档案先帮助理解人物，再逐渐增加复杂资料

**证据：** 已有知识人物条目、别名、说明，故事结构也有状态变化、认知与关联。见 [knowledge.ts:15–24](../../src/contracts/knowledge.ts#L15)、[story.ts:43–87](../../src/contracts/story.ts#L43)。

**建议：** 新手先填“想要什么、害怕什么、与当前冲突有什么关系”；口吻、经历、关系网以后补。“采访人物／整理人物特点”可作自愿创作练习，结果是候选，不自动决定人物正史。档案将长期特点和此时状态分栏。〔C01、P05〕

**代价与边界：** 低至中。不要把角色卡格式、人物问答或角色蒸馏变成写作前置流程；长期档案不能代替 DR-12 的时点状态。

### DR-07｜中｜改进机会：参考分析与本书设定应有明确转换动作

**证据：** 外部参考性质和出处已有；同一知识条目允许修改性质，并保留不可变历史。见 [knowledge-repository.ts:156–183](../../src/infrastructure/knowledge/knowledge-repository.ts#L156)、[knowledge.ts:26–44](../../src/contracts/knowledge.ts#L26)。这不等于当前发生了参考污染。

**建议：** 拆书输出只放“写作参考”，分清观察、原文证据和原创练习。借用灵感时另建自己的设定，并保留由哪个参考启发；不要原地把参考人物经历改成自己作品已经发生的事件。〔C02、C03、G01〕

**代价与边界：** 中低，需要来源及采用语义。先支持手工参考分析即可，不默认抓取商业小说、跨作品检索或自动仿写。

### DR-08｜高｜当前采用路径已确认：抽取时应先做实体消歧

**证据：** 单章知识提议采用时逐项调用 `createItemWithSources`，没有在这一采用路径中更新已有实体。见 [ai-repository.ts:525–534](../../src/infrastructure/ai/ai-repository.ts#L525)。已有别名、名称搜索和显式关联，不代表每次抽取都一定产生重复。

**建议：** 审阅时提供“关联已有阿禾／另建同名人物／暂不采用”。更新已有条目必须显示差异、保持来源和修订，不按同名自动合并。人物合并、纠错及撤销关系需要作者确认。〔P03、T03〕

**代价与边界：** 中，是一项作者消歧动作，不需要先引入自动实体解析模型。该新建路径由调查与主线局部核对支持，未计作独立复核通过的自动重复故障。

### DR-09｜中｜改进机会：版本保护之外，还需要看清改了什么

**证据：** 历史页有意只持有一个正文预览，AI 改写有原稿／新稿并排；正式历史页未提供两稿差异与命名入口。见 [RevisionHistory.tsx:48–72](../../src/renderer/components/RevisionHistory.tsx#L48)、[AiPanel.tsx:134–144](../../src/renderer/components/AiPanel.tsx#L134)。

**建议：** 增加可选命名检查点及两稿差异，先按章、必要时按块加载，避免同时装入许多长稿。恢复仍产生新版本；“修改冲突前”的版本和原定稿应继续保留。〔P08〕

**代价与边界：** 中。单稿预览是资源取舍，不是丢稿缺陷；独立复核确认了界面范围，持久恢复保护由架构调查支持而非该 UI 复核证明。

### DR-10｜中｜改进机会：定稿与交付应该有明确完成感

**证据：** 导出已经区分工作稿和定稿，并明示跳过从未定稿的章节。见 [EditingDialogs.tsx:50–58](../../src/renderer/components/EditingDialogs.tsx#L50)。

**建议：** 定稿前可选检查“本章变化是否完成、视角是否一致、占位是否处理”；导出前列出纳入与未纳入章节名称，允许作者主动部分交付。后续阅读模式服务整章通读。〔P09〕

**代价与边界：** 低至中。不是静默漏章修复，不要求先做自动投稿、收益预测或完整出版排版。

## 6. 长篇记忆：应该记住什么，怎样避免记错

### 6.1 当前链路已经做到哪一步

```text
保存正文 → 不可变版本、段落 ID、散列、同事务变更事件
   ├─ 本地整理：固定来源 → 分批投影 → 暂存产物 → 原子发布
   └─ 模型整理：完整单章预览 → 作者明确发送
       → JSON 与逐字引文核验 → 作者采用／拒绝
       → 知识、出处、审阅审计 → 已采用单章摘要 → 分层汇总

正文／知识／故事字段 → 分片 → 独立向量预览与小批发送
 → 词法／名称别名／显式实体／有界向量 → 排名融合
 → 作者手选片段及合格前文摘要 → 固定实际 messages 与预算
 → 明确发送 → 候选 → 作者改稿采用 → 新版本与事件
 → 来源变更后排除旧产物或拒绝旧候选 → 重新整理与审阅
```

代表性证据：[studio-repository.ts:332–364](../../src/infrastructure/storage/studio-repository.ts#L332)、[task-repository.ts:190–225、308–450](../../src/infrastructure/memory/task-repository.ts#L190)、[ai-repository.ts:505–544](../../src/infrastructure/ai/ai-repository.ts#L505)、[context-summary.ts:72–104](../../src/infrastructure/ai/context-summary.ts#L72)。

**已经存在但尚未运行验收：** 来源版本门禁、作者采用、分层摘要、关键词与混合检索、部分人物时点资料。

**仍需整合：** 自动模型维护、完整人物历史状态、完整视角上下文、恢复包与效果评价。进度文档部分描述比新人物源码滞后，应以读到的具体链路和验收边界共同判断。

### 6.2 推荐的记忆分工

| 层次 | 保存什么 | 用途与边界 |
|---|---|---|
| 权威资产层 | 原稿版本、作者设定与决定、故事记录、来源、采用审计 | 能恢复、能追溯；作者采用不是客观真实性认证 |
| 经历摘要层 | 章、卷、全书的经历概览、未解事项和不确定说法 | 回忆较长过程；不能代替精确原文或人物知情证明 |
| 当前场景资料层 | 本场目标、地点、人物有效状态、显式知情、必要证据 | 解决这一次写作任务；按时点和作用域选取 |
| 派生检索层 | 分片、词法索引、向量、排名、覆盖统计 | 可重建、可优化；相似不代表事实或资格合格 |
| 候选工作层 | AI 输出、作者修改、待确认抽取、影响建议 | 不自动进入已确认正文或设定 |

这不是要求马上新增五套服务。优先使用现有书内数据库和版本，逻辑责任分开即可。

### DR-11｜高｜语义粒度边界：一整条说明可能混合不同性质

**证据：** 知识条目只有一组性质、采用、新鲜度和冲突状态；正文投影取当前工作稿而非仅定稿。见 [knowledge.ts:15–24](../../src/contracts/knowledge.ts#L15)、[task-repository.ts:42–52](../../src/infrastructure/memory/task-repository.ts#L42)。

**风险条件：** “阿禾现在隐居，未来将成为领袖”放在同一说明中，仅靠一个 `nature` 不足以区分两句。工作稿中的尝试也不应被作者误认为定稿正史。

**建议：** 对会影响一致性的陈述拆小，分清现状、计划、信念和推断；界面明确当前使用工作稿还是定稿。先做规范和作者审阅，不必先建复杂事实推理引擎。〔T03、T04〕

**边界：** 现有系统提示已禁止性质提升；这是粒度与产品表达不足，不是全库混为事实的指控。

### DR-12｜高｜已独立复核：形成时间不等于完整历史人物知情

**证据：** 当前人物入口核对最新认知修订、主体、采用、新鲜度与形成时间；没有按目标时点选择过去的态度版本，也没有完整遗忘／替代状态。关系字段已有有效起止概念，但认知并未形成相同闭环。见 [character-context.ts:30–55](../../src/infrastructure/ai/character-context.ts#L30)、[story.ts:31–40、79–87](../../src/contracts/story.ts#L31)。

**例子：** 时点 10 相信门码 A，时点 30 得知门码 B。如果直接更新当前描述并保留形成时间 10，回写时点 15 就可能取到不合时点的描述。

**建议：** 以作者确认的认知记录保存有效区间或替代关系；区分知道、相信、误解、怀疑，避免仅覆写整张人物卡。先支持显式状态，不自动推演完整心智。〔T03〕

**不能扩大为：** “人物过滤完全没有”。当前模式已经减少输入，并对附加资料执行门禁；当前章原文、标题和要求仍可能含越界信息，系统明确不承诺整包逐句防剧透，见 [context.ts:51–57](../../src/infrastructure/ai/context.ts#L51)。完整视角属于已计划整合事项。

### DR-13｜高｜已独立复核：引文校验不是摘要语义认证

**证据：** 单章校验段落与逐字引文；上层校验每份下层摘要至少有引文，但摘要正文独立接受字段检查。见 [ai.ts:290–303](../../src/contracts/ai.ts#L290)、[ai-summary.ts:154–168](../../src/contracts/ai-summary.ts#L154)。

**风险条件：** 有一条真实引文，却用它支持了原文没有表达的因果；后续分层摘要重复该说法。作者编辑采用文本也可能补入没有依据的内容。

**建议：** 摘要分成已写变化、不确定陈述、未解事项；重要断言可以点到精确原文。审阅同时检查“引文在不在”和“是否真的支持结论”。抽样核对时记录误归因、遗漏、时点错误，不只记录 JSON 合法率。〔T03、T04〕

**边界：** 完整范围、版本、引文、采用事务都已存在。这里没有观测到模型幻觉，不能说当前摘要一定错，也不建议用另一个模型的肯定回答代替作者核对。

### DR-14｜中｜设计机会：推进依赖基线应对应完整复核动作

**证据：** 同一条目对同章的依赖取最高被引用修订；注释明确把补充较新引文视为推进该条目的复核基线，旧引用仍保留。见 [source-projection.ts:101–120](../../src/infrastructure/memory/source-projection.ts#L101)。

**风险条件：** 条目含多项旧稿结论，只补一处新稿引文，就按现有规则推进整体基线；作者可能并未理解这意味着全条目已复核。

**建议：** 首先在 UI 明示并要求确认旧陈述已检查；进一步可逐陈述记录依赖，避免一处新引文替代全部复核。未来删章、删除或替换设定，应保留历史并通过墓碑／失效状态排除当前召回。

**代价与边界：** 中。现有规则是明确设计，不应直接当成违反已知契约的 bug。直接来源版本门禁确实存在；E/F 这类补充命题未完成独立复核，保留为有局部证据的设计机会。

### DR-15｜中｜已确认上限：编号限扫会形成语义召回盲区

**证据：** 筛选后按片段编号最多比较 5,000 个向量，保留最多 100 个语义候选，再与词法等排名融合。覆盖不足明确提示，代码也标注为容量捷径。见 [memory-vector.ts:5–8](../../src/contracts/memory-vector.ts#L5)、[vector-repository.ts:424–460](../../src/infrastructure/memory/vector-repository.ts#L424)、[search-repository.ts:124–210](../../src/infrastructure/memory/search-repository.ts#L124)。

**风险条件：** 合格向量超过限扫范围，目标恰在后面的编号，并且问题只有同义表达、词法未命中。此时该片段无法成为这次语义候选。

**建议：** 先按实体、来源类型、时点等缩范围；需要更大覆盖时设计可继续的分区扫描、覆盖游标和确定性重排。只有实际召回与资源证据表明有必要，再评估 ANN 或专用向量扩展。〔T01–T03〕

**边界：** 不是“没有混合检索”，也不是已经测到长篇漏召回。D7 已计划容量与排名验收；返回条数和扫描覆盖必须分开显示。

### DR-16｜中｜改进机会：预算、缓存与上下文优先级需要任务化

**证据：** 输入按 JSON 的 UTF-8 字节数乘 1.1 加 1,024 余量估算，明确非精确 tokenizer；另有 80,000 字符限制，超限拒绝而非静默截断。向量 profile 绑定完整连接快照，连接保存会推进版本。见 [context.ts:20–21、237–275](../../src/infrastructure/ai/context.ts#L20)、[vector-repository.ts:40–42](../../src/infrastructure/memory/vector-repository.ts#L40)、[ai-repository.ts:246–274](../../src/infrastructure/ai/ai-repository.ts#L246)。

**建议：** 必保作者要求与改写目标，再选本场有效状态、精确证据，摘要只作背景。按类别显示预算与未选原因，用真实 usage 校准误差，不把用户填写的窗口当已验证容量。将向量语义兼容身份与展示名、输出预算、密钥更新区分，仍绑定模型代际、预处理、维度和同书身份。〔T01、T02、T04、T05、C03〕

**代价与边界：** 中低起步。字节估算是保守工程选择，不是假 token 数测量；供应商提示缓存也不同于本地 embedding 缓存，不能直接推断节省比例或默认兼容。

### 6.3 三条技术路线怎样选

| 路线 | 适用问题 | 主要局限 | 本项目建议 |
|---|---|---|---|
| 全书直接长上下文 | 小书、一次性全局阅读或对照 | 成本、位置敏感、修订与时点资格仍要管理〔T01、T02〕 | 可作为明确授权的可选任务，不做唯一记忆方案 |
| 分层摘要＋版本化资料＋混合检索 | 日常逐章写作、局部改稿、证据追溯 | 摘要误差、消歧、召回覆盖和来源失效需治理 | 保持为默认路线，优先补语义与作者工作流 |
| GraphRAG／LightRAG | 全书主题、势力关联、跨群体关系等全局查询 | 图构建与摘要成本；新增索引不等于删改、知情治理正确 | 借鉴分层与双层召回，不默认引入框架或图数据库〔T06、T07〕 |

MemGPT 的分层／虚拟上下文提供了“不能把所有东西常驻输入”的参考〔T08〕，但代理自己改记忆不应自动改作者正史。模型是候选产生者，版本化资产、有效时点和作者确认才决定可以使用什么。

## 7. 架构、可靠性与低资源技术建议

### 7.1 当前架构

```text
React / Tiptap
 → sandbox preload：有限 StudioApi
 → Electron main：页面来源核验、原生文件选择、AI 网络、草稿留存
 → utilityProcess：输入校验、串行领域队列
 → book.sqlite：正文、知识、故事、任务、候选、采用与 outbox
   studio.sqlite：书架目录缓存和书库锁
   sources/ 与 recovery/：数据库之外的独立资产
```

受限桥、指定主 frame 与 URL 检查、导航与权限限制是真实机制；utilityProcess 是故障隔离与分工，不天然等于低权限沙箱。见 [main/index.ts:75–79、363–383](../../src/desktop/main/index.ts#L75)、[preload/index.ts:14–122](../../src/desktop/preload/index.ts#L14)。〔A01、A02〕

### DR-17｜高｜明确待开发、独立确认：完整恢复资产闭包

**证据：** 升级副本仅备份数据库；原始导入字节另在 `sources/`，草稿在 `recovery/`。进度已经说明迁移副本不是 D6 完整恢复包。见 [studio-repository.ts:623–640、798–824](../../src/infrastructure/storage/studio-repository.ts#L623)、[draft-recovery.ts:64–72、149–151](../../src/desktop/main/draft-recovery.ts#L64)、[开发进度:513、543](../开发进度/开发进度-2026-11-06.md#L513)。

**建议：** 版本化清单记录作品身份、格式和最低读取版本、数据库一致快照、原始来源清单与散列、可选恢复稿、完成状态；明确排除密钥。恢复到新目录，失败保留原资产，恢复前预览包含哪些章节、历史和资料。〔A03、A04〕

**边界：** 现有备份和保稿保护不是无效机制，更不是“完全没有备份”。但正文 TXT／Markdown 和裸数据库文件都不能冒充完整恢复。正式交付前应完成此项；不提前执行数据库迁移或真实恢复实验。

### DR-18｜中｜已独立复核：部分写请求结果缺少跨进程耐久确认

**证据：** 通信回执最多 32 份内存缓存；service 先执行业务再发送响应，requestId 未统一进入新建／导入的业务事务。见 [service-client.ts:128–156](../../src/desktop/main/service-client.ts#L128)、[service/index.ts:111–125、151–162](../../src/desktop/service/index.ts#L111)、[studio-repository.ts:247–269](../../src/infrastructure/storage/studio-repository.ts#L247)。

**故障窗口：** 数据库已提交，业务进程在响应发出前退出。新生成的资产身份与原请求缺少持久映射，恢复后可能需要人工查目录才能确认。

**建议：** 只对必要写命令在同事务记录 requestId、输入散列和结果身份／版本，同 ID 异输入拒绝；不缓存整章内容，不自动重放未知命令。

**不能扩大为：** 32 条限制导致 SQL 数据丢失。当前超时占位、锁写、草稿留存、正文 CAS 和 AI run 状态读回都存在；结论仅是结果可判定性与人工恢复成本。

### DR-19｜中｜静态时序：来源文件与书内事务不是一个原子边界

**证据：** 文本导入先写原始来源文件，再书内提交，最后书架登记；完整孤立书可扫描重新登记，但不覆盖所有来源残留解释。见 [studio-repository.ts:544–590、619–657、684–712](../../src/infrastructure/storage/studio-repository.ts#L544)。

**建议：** 复用恢复清单或小型导入意图，记录来源散列、目标身份和阶段；提供“文件已写、正文已提交、书架已登记”的残留核对与继续／隔离入口，不自动删除。

**代价与边界：** 中。已有独占新文件写出、同步落盘及原字节保留；孤儿文件不等于覆盖旧稿。不需要引入跨文件分布式事务。

### DR-20｜中｜静态资源风险：草稿保护不应长期阻塞主进程回执

**证据：** 检查点容量核对和列表使用同步目录与文件操作，列表读取上限为 512 MiB；领域成功回执前可先执行辅助保存标记。见 [draft-recovery.ts:49–115、128–169](../../src/desktop/main/draft-recovery.ts#L49)、[service-client.ts:124–130](../../src/desktop/main/service-client.ts#L124)。

**建议：** 优先交付领域成功状态，辅助标记异步串行；扫描与解析分批让出，必要时独立恢复 worker，保留脱离业务进程的保稿能力。

**边界：** 已有文件数量、字节上限和“辅助失败不否定正文成功”的保护。这里只确认同步工作路径，不宣称测得卡顿或输入丢失。

### DR-21｜中｜技术机会：分批产物不等于所有 SQL／CPU 都有同样上限

**证据：** 本地每步 64 片段，但状态仍统计来源／事件；发布阶段一次登记整个批次；向量 finish 的事务内同步比较最多 5,000 个向量并统计覆盖。不可变正文与派生历史也会累积。见 [task-repository.ts:262–305、415–448](../../src/infrastructure/memory/task-repository.ts#L262)、[vector-repository.ts:328–365、424–460](../../src/infrastructure/memory/vector-repository.ts#L328)、[storage/schema.ts:75–106](../../src/infrastructure/storage/schema.ts#L75)。

**建议：** 先记录不含正文的排队／阶段耗时、实际行数、向量维度、库与 WAL 大小、产物覆盖；按修订复用统计。空间分类区分作者不可静默丢弃的正文／审计与可重建派生缓存，清理必须作者明确授权。

**代价与边界：** 低至中。D7 已计划性能与容量；不能因为函数返回 limit 就声称处理只涉及 limit 条，也不能在无测量时宣称性能不够。

### DR-22｜中｜明确待验收：版本、原生依赖与提供商能力矩阵

**证据：** 已有显式备份后升级、未知版本拒绝；AI 按兼容接口字段发送并核对结束状态。当前没有安装锁文件和实际 Electron ABI／SQLite 内核／FTS5 运行证据。见 [studio-repository.ts:125–145、780–858](../../src/infrastructure/storage/studio-repository.ts#L125)、[package.json:17–37](../../package.json#L17)、[ai-sessions.ts:590–596、727–748](../../src/desktop/main/ai-sessions.ts#L590)。

**建议：** 在获准安装与验收后，固定真实依赖、可读／可升级／不可降级范围；对用户指定提供商核对结构输出、断流、取消、用量未知和输入限制。展示 session key 的保存边界，不能把“兼容 API”当支持所有供应商的证明。〔A01、A03、A05〕

**边界：** 本轮部分 AI 官方协议页面未取得正文，不作供应商协议违约判断。已有不自动迁移、不自动重试或切备用地址的保护，应继续保留。

### 7.2 本机最小成本路线

保留单业务进程、每书 SQLite、单章编辑、FTS5、有界向量和作者明确采用。优先顺序是：**可恢复 → 结果可判定 → 可观察 → 有证据再优化**。

本轮不建议默认增加数据库服务器、图数据库、独立向量服务、本地大模型、常驻自动正史代理或每书一个后台服务。它们会增加部署、内存、权限和故障面，不能解决原稿恢复或人物时点语义。

### 7.3 外部资料和角色卡的安全边界

当前提示已明确只有任务类型和作者要求表达指令，原稿、证据、标题与摘要是资料。见 [context.ts:22–57](../../src/infrastructure/ai/context.ts#L22)。这与 OWASP 的“标记外部内容、约束模型、校验输出、最小权限、高风险人工确认”方向一致〔G01〕。

但提示注入不存在仅靠 system prompt 就能保证消除的结论。角色卡 V2 的系统提示字段、V3 的 PNG 元数据／CHARX 资产，应作为不可信资料处理：

- 若只映射人物资料，就明确标为**资料级导入**，不宣称完整执行兼容；不自动替换工作台系统规则。
- 外链不自动抓取；压缩资产限制数量、总尺寸和路径，不执行脚本或 HTML。
- 预览将发送的范围和接收接口；不把密钥写入作品或恢复包。
- 不新增默认自动发布、远程写文件或自动改变正史的权限。

这是未来交换功能的设计要求，不是声称当前已经存在通用角色卡导入漏洞。NIST 资料仅用于支持贯穿设计、使用、评价的风险管理口径；本轮只读取出版页摘要，没有读取完整风险条目〔G02〕。

## 8. UI：从“管理系统”转向“完成这一章”

### DR-23｜高｜信息架构机会：主任务与系统整理应有层级

**证据：** 正式入口以书架／正文为主，顶部并列作品资料、知识库、故事记录、记忆检索、章节整理、分层汇总、导出，主要能力进入模态面板。见 [App.tsx:609–638](../../src/renderer/App.tsx#L609)。

**建议：** 写作默认只保留章节、正文、AI 建议、保存／专注；其他分成“资料”“整理与审阅”“版本与恢复”。高级工具按需展开，保留完整入口，不让作者误认为需要先整理记忆才能写。〔U04〕

**边界：** 入口并列可静态确认，实际拥挤、溢出或认知负担未被使用研究证明。不必为了导航立即实现 v4 全部十三页。

### DR-24｜高｜交互机会：明确发送、生成、作者改稿和正文保存的去向

**证据：** 实际接口／messages／预算预览已有，“本地保存预览”和“确认发送”分开；原提议持久化，未采用作者修改离开时要处理，生成时不能直接关面板。见 [AiPanel.tsx:110–144、327–331、819–834](../../src/renderer/components/AiPanel.tsx#L110)。

**建议：** 首层显示“会发给谁、当前章范围、附加资料数量、是否已发送、费用是否可估”；完整指纹继续折叠。持续区分“原提议已留存、你的修改尚未留存、尚未进入正文”。先提供复制改稿再离开的出口，随后评估持久暂存和返回正文审阅。

保存位置统一显示状态＋下一步：失败先保留／重试；结果未知先核对；冲突先另存再重载。草稿副本不能写成正文已保存。〔U03、U04〕

**代价与边界：** 文案与层级为低，持久暂存和生成时切回正文为中。现有门禁是在保护作者，不应只删除确认或换个按钮名。

### DR-25｜中｜显式策略机会：焦点、状态、来源跳转与返回

**证据：** 共享 Dialog 已有原生 `showModal()`、标题关联及回焦，小表单有 autoFocus；长 AI 面板的放弃确认追加在底部，未给该确认独立聚焦／滚动策略。来源能读固定版本副本，但尚未形成完整正文定位和返回链。见 [Dialog.tsx:16–24](../../src/renderer/components/Dialog.tsx#L16)、[AiPanel.tsx:128、833–834](../../src/renderer/components/AiPanel.tsx#L128)、[KnowledgePanel.tsx:319–323](../../src/renderer/components/KnowledgePanel.tsx#L319)。

**建议：** 长面板聚焦标题，确认优先聚焦安全选项；结束／失败用稳定状态区播报，不逐字朗读流式输出。当前锚点仍存在时定位正文；历史稿只读侧读，失效锚点不猜替代段落；保留返回建议、选区、滚动和焦点位置。〔U01、U03〕

**边界：** 不是所有对话框没有焦点陷阱，更没有观察到实际读屏失败。现有 select／radio 不需要硬改成 combobox；只有设计为输入＋弹出选择时才适用相应契约〔U02〕。

### 8.1 推荐默认布局与旅程

```text
书架 / 当前作品 / 第一章           保存状态   保存   专注

章节目录（可收起） │              主编辑区
                  │  可选三问：想得到什么 / 什么阻碍 / 结束变化
```

新手故事时点优先显示“这个场景发生在某事件之前／之后”，排序值留在高级说明；必须与实际作者时间模型一致，不偷偷按章节顺序猜时间。真实颜色对比、溢出、遮挡、输入法、键盘、读屏与长列表响应仍需运行验收。首期定位 Windows 桌面，不将手机尚未完成列为首期缺陷。

## 9. 推荐产品推进顺序

### 9.1 面向零经验作者的八步脚手架

1. 先定一个小目标：完成一章，不要求马上规划百万字。
2. 写一句故事种子：人物、欲望、阻力和不行动的代价，可不完整。
3. 确定第一章前后变化，例如从相信证词到决定调查。
4. 可选列一至三场：每场有目标、阻力和结束变化。
5. 选择当场视角及必要资料；复杂人物传、世界百科以后补。
6. 写粗稿，允许占位；AI 是可选辅助，不是开始条件。
7. 先改因果与场景作用，再改人物／信息，最后改语言与对话。
8. 通读、看版本变化、确认本次定稿和导出范围。

这些问题是可调整脚手架，不保证创作成功，不以字数或商业指标评价作者。

### 9.2 建议安排，不缩减已承诺范围

| 阶段 | 推荐补充工作 | 可观察结果 |
|---|---|---|
| 产品规格补齐 | 整理现行功能范围；标清历史、原型、源码、待开发和验收；确认章／场、人物状态和参考采用语义 | 不再靠缺失 PRD 或原型页面推断正式范围 |
| 优先串联创作 | DR-01–04、DR-08；必要作品约定和轻量人物提示 | 作者能从种子到一章，并知道为什么改稿 |
| 完善审阅与资料 | 版本对照、来源定位、作者改稿稍后处理、计划／事实／参考的转换 | 能解释资料来源和修改结果 |
| 整合记忆治理 | 人物有效状态、摘要支持关系、消歧、依赖复核、召回覆盖与预算 | 有界、可追溯，不夸大知情或防错 |
| 完整交付条件 | 恢复包、跨进程确认、资源观测、兼容矩阵 | 可恢复、可判定；不把导出当备份 |
| D7 获准后统一验收 | 真实应用、故障、长篇、质量、成本、可访问性 | 以实际证据决定是否需要更重技术 |

现有 D6 的图谱、时间线、阅读、方法、偏好与完整恢复继续按已确认范围推进；本报告不擅自删减。上述建议进入实施前，还需具体任务范围、接口／迁移和产品取舍确认。

## 10. 以后获得授权才执行的验收矩阵

本节只提出人工场景和测量口径，没有编写或执行单元测试，也没有授权任何本机高资源操作。项目的统一验收安排仍以开发进度为准。

### 10.1 不只看“能装下多少万字”

30 万、100 万、200 万字样例可作为容量档位，但还应记录章节数、实体数、别名密度、倒叙／视角数量、修订频率、实际 token、片段数、向量维度与机器配置。相同字数可以有完全不同的难度。

| 场景 | 应检查什么 | 必须保留的证据 |
|---|---|---|
| 零经验首章 | 无世界观、无模型时是否能开始；提示能否跳过 | 实际步骤、阻塞点、作者对下一步的解释 |
| 同章多场 | 目标、定位、视角与移动是否清楚 | 场景清单、正文锚点、修改前后版本 |
| 倒叙与多视角 | 章序、故事时间、读者揭示和人物知情不互相推导 | 所选时点、认知状态、实际 messages、越界案例 |
| 人物认知更新 | A→B、误解纠正、隐瞒与遗忘 | 有效区间、来源、当前／历史查询结果 |
| 同名与别名 | 同一实体可关联，同名实体不自动混并 | 原实体 ID、作者消歧、错误合并与修正记录 |
| 摘要质量 | 关键变化、因果和未解事项是否被正确压缩 | 每项断言与原文支持、遗漏／错误分类 |
| 修改设定／追加新引文 | 影响状态是否维持到复核，不只靠新引用推进 | 旧新 revision、依赖、作者确认、发布批次 |
| 拒绝候选／工作稿与定稿 | 拒绝和实验稿是否进入不应进入的范围 | 作者决定、选取范围、召回结果、最终输入 |
| 删章／重排／替换资料 | 当前召回与披露失效正确，历史仍可读 | 墓碑或失效记录、章序、原稿和历史锚点 |
| 罕见词、别名、同义问句 | 词法与语义的覆盖、排名和支持证据 | 合格总数、已索引／已扫描数、候选与 Recall@k |
| 超出限扫范围 | 不把局部 Top-k 说成全书最佳 | 扫描边界、继续查询、命中／漏召回样例 |
| 大输入与预算 | 改写目标不被删，估算和实际用量差异可解释 | 实际 messages、类别预算、usage、超限处理 |
| 跨作品隔离 | 不召回另一书的资料或误用连接／密钥 | 作品身份、来源、连接作用域、拒绝结果 |
| 提交后回执前退出 | 能确认原操作结果，不自动产生第二份资产 | 请求身份、结果映射、CAS、恢复选择 |
| 导入阶段中断 | 来源已写／数据库已提交／书架已登记可解释 | 意图阶段、散列、残留清单、原文件保留 |
| 恢复包与旧版本 | 恢复到新目录后正文、定稿、知识和来源一致 | manifest、快照、散列、版本与失败保留 |
| 长篇资源 | 产物步、统计、发布、向量比较、恢复扫描分别有界 | 队列和阶段耗时、内存、行数、WAL／库尺寸 |
| 提示注入与角色卡 | 外部资料不改变权限、不自动抓外链或写正史 | 原输入、实际 messages、权限边界、作者动作 |
| 键盘／读屏／IME | Tab、Escape、回焦、状态、中文组合输入、撤销 | 实际设备／浏览器／Electron版本与操作记录 |

### 10.2 指标与结论怎样分开

- **检索层**：Recall@k、排序、证据是否属于正确实体／时点／版本；覆盖不足单独统计。
- **摘要层**：关键事件遗漏、无支持断言、错因果、错时点、混入计划／人物信念；不能只统计格式正确。
- **生成层**：人物越界知情、规则违背、误用未来计划、错误引用；允许作者主动有意偏离并记录。
- **可靠性层**：提交原子性、结果确认、恢复资产一致性；不得由模型回答代替数据库证据。
- **体验层**：完成任务的实际步骤、停顿与回退、作者是否理解下一步及各保存状态，不预填满意度。
- **资源与费用层**：实际 usage、请求次数、缓存命中、阶段耗时、内存和磁盘；未返回用量写未知，不写虚构价格。

〔T01–T03〕只印证为什么要分解这些能力，不提供本项目成绩，也不是针对中文小说的现成验收集。

### 11.2 本轮实际方式

- 读取现行文档、关键契约与真实调用链，按当前工作树而非只按 Git HEAD 判断。
- 五条专题调查与两条小范围独立复核；主线对重点字段、采用、检索和当前 UI 再核对。
- 查阅官方产品文档、格式规格、公开论文摘要／可获得部分正文及工程规范；没有上传本地正文、代码、日志或密钥。

- 报告及索引执行轻量文本、路径、链接和差异检查；不把这些写成项目测试、编译或 UI 验收。
