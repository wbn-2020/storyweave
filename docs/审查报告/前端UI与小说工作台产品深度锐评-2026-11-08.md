# 前端 UI 与小说工作台产品深度锐评

编写日期：2026-11-08（Asia/Shanghai）。
评审对象：织章 · StoryWeave 当前桌面客户端实机界面、`src/renderer/` 正式前端源码、`docs/` 既有产品与审查文档，以及本地小红书小说工作台参考设计（`C:\Users\Administrator\Desktop\pict\小说工作台\01.png`–`04.png`「莓糖星图」）。

> **核心结论：**
> GPT 交付的这套前端 UI 与产品交互，本质上是**“用数据库运维后台的思维，套了一层 2015 年企业 OA 系统的蓝白皮，再把 26 个功能模块粗暴地塞进弹窗里”**。它在底层防丢稿、防剧透、版本 CAS 校验上投入了过度偏执的工程精力，却把所有系统复杂度原封不动地甩到了小白作者脸上；更荒诞的是，它后期补齐的大批源码根本没有重新编译进 `out/`，导致用户桌面快捷方式启动的甚至还是一个顶着 Electron 默认原子图标的半成品旧构建。

## 一、 破案现场：为什么你双击桌面图标看到的界面如此简陋？

在锐评视觉和产品逻辑之前，静态核查源码与构建产物后发现了三个令人啼笑皆非的工程事实：

### 1. 源码改到了 v14，但编译产物还停留在旧版（“未编译交付”）
- 对比实机截图与当前源码 [App.tsx](../../src/renderer/App.tsx#L874-L883)：
  - **你的实机截图左侧栏**：「故事空间」下只有 **4 项**（`故事设定`、`关系星海`、`故事时间线`、`灵感与笔记`）。
  - **当前 `src/renderer/App.tsx` 源码**：「故事空间」下明明写着 **8 项**（新增了 `规划与审稿`、`创作日历`、`封面与人物立绘`、`全局灵感收件箱`），且新建作品弹窗已改为带“故事种子三问”的 [NewBookDialog.tsx](../../src/renderer/components/NewBookDialog.tsx#L13-L50)。
- **原因何在？** 翻看 GPT 自己撰写的 [开发进度-2026-11-06.md](../开发进度/开发进度-2026-11-06.md#L758) 第 758 行与第 810 行，上面赫然写着：
  > *“本节只记录源码实现与静态检查。上方同日 UI 批次的类型检查、构建和浏览器结果发生在本轮修改之前……本轮没有生成新构建，现有桌面产物不代表这些源码。”*
- 换言之，GPT 在最后两个开发批次里往 `src/` 塞了上万行代码（把作品库 schema 从 v12 升到 v14），**却压根没有执行构建去更新 `out/` 目录**！你现在双击桌面快捷方式运行的，依然是更早之前那版“空壳蓝白 UI”。

### 2. 桌面快捷方式“裸奔”顶着 Electron 默认原子图标
- 查看打包脚本 [package-windows.mjs](../../scripts/package-windows.mjs#L89-L112)，GPT 在 `electron-builder` 配置里将 `directories.buildResources` 指向了一个每次打包时用 `mkdirSync(resourceDir)` 临时创建的**空文件夹**，全仓库没有任何 `.ico` 应用图标配置。因此生成的桌面快捷方式只能顶着 Electron 原生默认的蓝白原子图标，毫无品牌完成度。

### 3. `design/` 下的 6 套原型与 `src/renderer/` 正式代码严重割裂
- 仓库 `design/` 目录里躺着 `ui-v1` 到 `ui-v6` 六套纯静态 HTML 演示页（甚至 [ui-v5](../../design/ui-v5/README.md) 做了宣纸朱砂风、[ui-v6](../../design/ui-v6/README.md) 做了莓糖书房风），但它们全是不接数据库、刷新即清空的单页玩具；而真正跑在 Electron 里的 `src/renderer/` 正式前端，却是一套拼凑出来的工业风表单系统。

## 二、 行业调研与小红书案例拆解：一个优秀的「小白长篇小说工作台」应该怎么设计？

结合你提供的小红书高赞参考图（`01.png`–`04.png`「莓糖星图」）以及国内外成熟小说创作工具（Novelcrafter、Sudowrite、Scrivener、Plottr、Dabble、橙瓜码字）的设计范式，一个真正能让**零经验小白直接上手写长篇**的工作台，必须解决小白的三大核心痛点：**“开篇对着白纸发呆”、“写到三万字设定伏笔全乱”、“卡文时不知道怎么往下接”**。

### 1. 情绪价值与“沉浸式书房氛围”（而非 B 端管理系统）
- **参考对照（小红书 `01.png` & `03.png` 莓糖星图）**：
  - 写小说是高度感性的脑力活动。莓糖星图采用了**“莓果奶霜 / 暮色紫藤 / 鼠尾草绿”**等低饱和度柔和色调，配合富有故事感的插画横幅（*“让人物带着秘密，走进下一幕”*）、手写体批注（*“每个故事，都值得有一间房”*）以及拟物化的立体书脊书架。
  - **设计法则**：软件第一眼必须提供**“安静、温暖、有呼吸感的私人书房仪式感”**。纸张底色要温润护眼，控制面板要退居幕后，杜绝刺眼的纯白 `#FFFFFF` 底板配高饱和工业亮蓝 `#0865D1`。

### 2. 从“一个脑洞”到“一章正文”的渐进式脚手架（Progressive Onboarding）
- **小白为什么不敢动笔？** 因为传统软件一上来就让他建文件夹、建卷、填几十个世界观设定字段。
- **参考对照（小红书 `02.png`「一个脑洞，怎么长成一部小说？」）**：
  - **第一步（轻设定）**：“世界的规则，一条条长出来——先选分类，再添加规则。可以少写、留空、删除或调整顺序。”不给新手任何填空压力。
  - **第二步（章节规划 / Story Garden）**：“让已有的文字，长出下一章”——作者只需勾选参考哪一章、带入哪两条人物关系，底下直接提供一个傻瓜式主按钮：**`+ 帮我连接下一章（仅一章）`**。
  - **设计法则**：新手引导绝不是“01 选文件夹 → 02 建文件 → 03 去写字”的操作说明书，而是**创作思维脚手架**：`一句话脑洞/主角执念` ➔ `自动生成三幕或首章小节拍` ➔ `点击节拍直接扩写成正文`。

### 3. 全画布可视化理清脉络（消灭弹窗与 CRUD 数据库表单）
- **长篇为什么容易崩？** 因为人物关系变了、伏笔埋了忘了收、故事发生时间与叙述顺序倒挂。
- **参考对照（小红书 `04.png`「人物关系、伏笔、时间线一眼理清」）**：
  - **关系画布**：不是冷冰冰的 SVG 圆点，而是**带人物头像、角色定位标签（女主角/关键人物）、场景照片（月光便利店）、关键道具（旧日照片）的视觉卡片网络**，连线上清晰标注“好友 / 兄妹 / 调查 / 对立”。
  - **时间线**：横向时间轴卡片（第1章 意外的夜班 ➔ 第2章 她的第一位客人 ➔ 第3章 收据上的空白），顶部一键切换**「叙述顺序 / 故事时间」**，底部直观分栏**「过去：埋下的伏笔 / 现在：故事正在发生 / 未来：未解的谜团」**。
  - **设计法则**：设定、画布、时间线、大纲应当是**平铺在主工作区的独立视图（First-class Views）**，所见即所得、直接拖拽编辑，而不是点一个按钮弹一个模态框。

### 4. 把复杂 Prompt 封装成“点菜式技能库”（Skill Cards & Copilot Drawer）
- **小白为什么用不好 AI？** 因为小白不会写复杂的 Prompt，更看不懂什么“上下文窗口预算、Token 估算、向量召回率”。
- **参考对照（小红书 `03.png`「03 拆书导入 & 04 技能库」）**：
  - **拆书工作流**：把读过的好书导入，直接提炼成可视化的标签胶囊（`人物关系`、`世界设定`、`核心主题`、`金句摘录`、`写作手法`、`情节结构`），写文时一键勾选调用。
  - **内置技能库**：把专业写作技巧封装成具象卡片——`场景描写（把抽象情绪写成场景）`、`异常物延迟解释（先制造异常，再逐步揭晓）`、`单感官段落`、`伏笔回收检查`、`角色动机追问`、`场景冲突递增`。
  - **伴随式 AI 副驾驶**：在写作页右侧提供可折叠的轻量化 AI 抽屉，选中正文一段话即可呼出“用技能改写 / 追问动机 / 检查伏笔”，对比后一键替换。

## 三、 狠狠锐评 GPT 做的前端 UI 与交互设计：四大罪状

对照上述黄金标准，再看 GPT 在 `src/renderer/` 中写出的真实代码与界面截图，其问题之严重，绝非“微调几个颜色”能掩盖：

### 罪状一：把“苹果风”做成“政务 OA / 医院挂号后台”，毫无文学与创作美感
- GPT 在 [苹果风格界面设计与适配-2026-11-08.md](../产品文档/苹果风格界面设计与适配-2026-11-08.md#L35) 中声称参考了 Apple HIG、Apple Books 与 Apple Notes，但实际写出的 [App.module.css](../../src/renderer/App.module.css#L1-L70) 和 [WelcomeWorkspace.module.css](../../src/renderer/components/WelcomeWorkspace.module.css#L1-L71) 却是：
  1. **配色冰冷刺眼**：大面积 `#edf0f5` 冷灰外框 + `#ffffff` 纯白背景 + `#0865d1` 高饱和企业蓝按钮。这种配色属于典型的政企 SaaS 报表后台或系统设置面板，完全抹杀了小说创作所需的沉浸感与温度。
  2. **极其敷衍的排版与留白**：
     - 首页（`image.png`）中间四个统计数字（`写作中作品 — | 当前作品章节 — | 正文总字符 — | 已定稿章节 —`）用生硬的 `1px solid #e0e2e6` 竖线切开，排得像财务后台的 KPI 监控栏；
     - 空状态下的 `开始你的第一部作品（01 选择作品库 / 02 新建或导入作品 / 03 正文与设定一起展开）` 就是三列干巴巴的 12px 灰字说明，连卡片容器都没有，视觉重心完全散架；
     - 甚至在上一版构建（`out/参考布局工作台-2026-11-08.png`）里，GPT 为了模仿你的参考图，居然直接从 `01.png` 里把别人的便利店插画裁切下来保存成 `src/renderer/components/workspace-banner.png` 贴在页面上；被要求改苹果风后，又直接删掉插画换成一个死板的深蓝方块 `你的故事从此开始`。两边走极端，毫无原创设计能力。

### 罪状二：“阴阳脸”主题精神分裂——外层刺眼纯白，点开弹窗瞬间掉进煤矿黑洞！
- 这是当前 `src/renderer/` 代码中最离谱的视觉割裂：
  - 查看全局样式表 [tokens.css](../../src/renderer/tokens.css#L1-L26)：`:root` 定义的是一套**暗黑深空主题**（`color-scheme: dark`、`--color-bg: #10151b` 黑蓝底、`--color-surface: #171f28`、`--color-accent: #d8bd91` 暗金黄）；
  - 到了“苹果风改造”时，GPT 偷懒没有重构全局 Token，而是在 [App.module.css](../../src/renderer/App.module.css#L36) 里只给 `.main`（主画布）和 `.lightDialog` 强行局部覆盖了亮白色变量（`--color-surface: #fff`、`--color-accent: #0865d1`），并在 [苹果风格界面设计与适配-2026-11-08.md](../产品文档/苹果风格界面设计与适配-2026-11-08.md#L40) 第 40 行留下一句免责声明：*“复杂业务面板仍有既有深色样式，未在本轮宣称全应用主题切换完成。”*
  - **实际后果有多惊悚？**
    在 [App.tsx](../../src/renderer/App.tsx#L962-L995) 中，只有 `newBook`、`workbench`、`inspiration`、`calendar`、`media` 几个弹窗传了 `className={styles.lightDialog}`；而最核心的 **「故事设定 (`KnowledgePanel`)」、「关系星海 (`StoryGalaxyPanel`)」、「故事时间线 (`StoryTimelinePanel`)」、「故事记录 (`StoryPanel`)」、「灵感与笔记 (`NotesPanel`)」、「AI 协作 (`AiPanel`)」、「版本历史 (`RevisionHistory`)」** 全部使用的是默认深色 `<Dialog>`！
  - 用户在纯白亮蓝的首页或写作页上，只要点一下「故事设定」或「AI 协作」，屏幕中央立刻炸出一个 **`#171f28` 乌黑背景、`#121b24` 黑底输入框、`#d8bd91` 暗金色按钮**的巨型弹窗！同一个软件里，一半弹窗是“白昼苹果蓝”，一半弹窗是“暗夜煤矿金”，审美分裂到了极点。

### 罪状三：反人类的“弹窗地狱（Modal Hell）”——26 个模态框彻底摧毁创作流
- 打开 [App.tsx](../../src/renderer/App.tsx#L55-L61)，你会看到一个令人窒息的架构设计：
  - 主视图 `StudioSurface` 只有区区 3 个：`'home' | 'shelf' | 'write'`；
  - 而模态弹窗 `Modal` 竟然定义了 **26 种**：从故事设定、关系星海、时间线、规划与审稿、创作日历，到 AI 协作、版本历史、记忆检索，**统统都是 `<dialog>` 模态弹窗！**
- **为什么说这是对小说工作台的毁灭性打击？**
  1. **假导航栏，真弹窗触发器**：左侧导航栏「故事空间」下的 8 个入口，看着像页面导航，实际上每个按钮都写着 `aria-haspopup="dialog"`。点任何一个，都不是切换主工作区，而是弹出一个宽 940px 的模态窗口把整个屏幕遮住！
  2. **弹窗内套娃切换**：比如你在「关系星海」弹窗里想改一条人物设定，点击后它会关掉星海弹窗、再弹出一个「故事设定」弹窗；关掉之后你已经忘了刚才在写哪一章。
  3. **AI 协作竟然也是全屏模态弹窗！** 在 [App.tsx](../../src/renderer/App.tsx#L945) 中，正文编辑器写着 `disabled={studioView !== 'write' || busy || bookRecoveryLocked || Boolean(modal)}`。也就是说，当你点击「AI 协作」想让 AI 帮你续写或改写时，**一个巨大的暗黑弹窗直接把你的小说正文遮得严严实实，且底层正文被强制锁死**！你根本无法一边看着正文上下文、一边在侧边栏和 AI 互动。

### 罪状四：把底层工程数据裸露给用户的“防御性焦虑 UI”
- GPT 在前端界面上几乎没有任何“产品包装”意识，直接把后端 SQLite 表字段、SHA-256 哈希和容灾状态怼到了用户眼前：
  1. **满屏哈希与内部 ID**：在 [AiPanel.tsx](../../src/renderer/components/AiPanel.tsx#L128-L150) 和 [KnowledgePanel.module.css](../../src/renderer/components/KnowledgePanel.module.css#L54) 里，直接向小说作者展示：`任务 item.taskId · 节点 item.nodeId · 采用记录 item.runId · 来源清单 item.manifestHash · 覆盖指纹 item.coverageHash`、`人物修订 character.personRevisionId`、`提示版本 context.promptVersion`。小白作者看到这堆天书只会怀疑自己打开了调试控制台。
  2. **用“手填排序字符串”代替可视化时间线**：在人物视角和故事时间线里，要求作者手动填写抽象的 `作者排序值 (storyOrder)`，而不是通过拖拽卡片或选择“第几章之前/之后”来自动维护顺序。
  3. **荒唐的“手动复制 JSON 灾备框”**：在 [NewBookDialog.tsx](../../src/renderer/components/NewBookDialog.tsx#L45) 等表单组件里，一旦请求超时，界面竟然弹出一个只读 `<textarea>`，里面装着 `JSON.stringify({ mode, title, firstChapterTitle, protagonist, desire, obstacle })` 的原始 JSON 代码，逼着用户手动复制 JSON 并勾选“已留存表单”才能继续！把本该由前端 `localStorage` 或 IndexedDB 静默兜底的草稿缓存，做成了让用户手抄 JSON 的奇观。

## 四、 深度审视 GPT 的设计文档体系：30% 的严谨底座与 70% 的纸面教条

我们对 `docs/` 目录下的全套文档（产品设计基线、苹果风格界面设计、两次深度审查报告、两轮功能补齐说明、技术架构与开发进度）进行了交叉复核，客观评价如下：

### 1. 文档中值得保留的 30%（底层数据契约与安全边界）
GPT 在 [产品设计基线-2026-11-03.md](../产品文档/产品设计基线-2026-11-03.md) 与 [小说工作台设计与长篇记忆深度调研-2026-11-06.md](小说工作台设计与长篇记忆深度调研-2026-11-06.md) 中建立的几个**底层业务不变量**是扎实且正确的：
- **AI 生成是“候选提议”而非直接覆写**：所有续写、改写、抽取、拆书结果先作为候选保存，经作者确认后才推进正文或设定版本（CAS 乐观锁保护），绝不静默篡改原稿。
- **三层事实隔离（防剧透与防设定污染）**：明确区分「作者全知设定 (`author_setting`)」、「角色在特定时点的主观认知 (`character_belief`)」与「读者已披露范围 (`readerDisclosure`)」；同时将「拆书外部参考 (`external_reference`)」隔离在独立的 `inspiration.sqlite` 中，避免把别人的小说情节污染进自己的作品正史。
- **本地优先与单书 SQLite 架构**：每部作品独立 `book.sqlite`，配合快照、版本历史与恢复包校验，技术选型符合个人桌面端定位。

### 2. 文档中严重失职的 70%（为什么文档写了几万字，做出来却极其难用？）

| 维度 | GPT 文档的表现与问题根源 | 对产品的实际危害 |
| --- | --- | --- |

## 五、 重构路线图：如何把「织章 StoryWeave」真正变成惊艳的小白小说工作台？

既然底层 SQLite 仓储、IPC 通信、版本控制、AI 上下文组装与拆书/大纲/日历契约（book v14）已经写好，**最明智的做法是保留 `src/infrastructure/`、`src/desktop/` 与 `src/contracts/` 的坚实底座，对 `src/renderer/` 前端界面与交互动线进行彻底的“换皮与破壁重构”**：

### 1. 彻底消灭“弹窗地狱”，升级为「全画布多视图工作台」
- 将 `StudioSurface` 从仅有的 `home | shelf | write` 扩展为真正的**一级主画布视图**：
  - **🏠 今日书桌 (`home`)**：温润的书房主页（继续写作英雄横幅 + 今日码字打卡环 + 待收伏笔提醒 + 快捷进入各视图）。
  - **✍️ 沉浸写作 (`write`)**：左侧可折叠卷章/场景目录树 + 中央仿真书页稿纸 + **右侧伴随式双模抽屉（一边查「本场设定/人物/伏笔」，一边直接用「AI 副驾驶 & 技能卡」，彻底把 `AiPanel` 从全屏黑弹窗改为右侧常驻副驾驶抽屉！）**。
  - **🗺️ 章节规划与大纲 (`workbench`)**：主画布直接平铺「故事种子 ➔ 章节卡片看板（像小红书 `02.png` 那样展示章节卡片与 `+ 帮我连接下一章`）➔ 场景节拍」。
  - **📖 故事设定与人物卡 (`knowledge`)**：主画布平铺，人物采用**带立绘头像、核心欲望/弱点胶囊标签、关系跳转的精美角色卡**，世界观采用分类规则卡片（对标小红书 `02.png` 的 `01 故事设定`）。
  - **🌌 关系画布与时间线 (`galaxy` / `timeline`)**：主画布平铺，关系图使用带头像与关系标签的圆角实体卡（对标小红书 `04.png`）；时间线采用横向/纵向可视化双轨时间轴（叙述顺序 vs 故事时间，过去伏笔 / 现在事件 / 未来谜团）。
  - **💡 拆书、灵感与技能库 (`inspiration` / `notes`)**：主画布平铺，把 6 种内置写作方法 + 拆书提炼出的方法做成直观的**「技能卡片网格」**（对标小红书 `03.png` 的 `04 技能库`）。
  - **📅 创作日历与书架 (`calendar` / `shelf`)**：主画布平铺，拟物化立体书脊书架 + 创作心情/字数日历。
- 仅保留真正需要临时打断的操作（如“新建作品向导”、“导入/导出文件确认”、“恢复包选择”）使用轻量弹窗。

### 2. 终结“阴阳脸”，建立统一的「书房美学主题系统」
- 废除当前 `:root` 暗黑配局部 `.lightDialog` 亮蓝的分裂写法，将全局 CSS 变量重构为**四套可一键切换的工作室氛围配色**（参考小红书 `03.png` 右下角与 `design/ui-v5`、`ui-v6` 的精髓）：
  1. **🌸 莓果奶霜（默认温暖浅色）**：暖奶白纸面 `#FDFBF9` + 柔和樱粉玫瑰强调色 `#D84B7E` + 温润深褐墨字 `#2B1E26`（年轻化、小红书高颜值治愈感）。
  2. **📜 宣纸朱砂（东方书卷风）**：温润宣纸 `#F6F2EA` + 朱砂印章红 `#B2462B` + 松烟墨字 `#201F1B`（沉静、适合悬疑/古风/严肃文学）。
  3. **🌿 鼠尾草绿（护眼森系风）**：浅雾绿底 `#F3F6F4` + 森林绿强调色 `#3B6E5C`（适合长时间连载码字）。
  4. **🌙 墨夜星海（统一深色模式）**：全应用统一的夜航深色主题，不再出现“外白内黑”的割裂。

### 3. 给小白做“减法包装”，把工程复杂度藏回幕后
- **隐藏哈希与内部 ID**：默认界面上彻底隐藏 `taskId / nodeId / runId / manifestHash / coverageHash / personRevisionId`，将这些工程审计信息收进二级折叠的“高级技术详情”中。
- **一键式新手破冰**：在空白章节或章节规划页，直接提供可视化的「首章三问引导卡」与「勾选本章出场人物 + 选用一张技能卡 + 一键生成下一幕草稿」的极简动线。
- **静默自动升级与草稿兜底**：将“手动复制 JSON 留存框”改为前端本地自动暂存；将应用图标、最新 v14 代码完整编译打包，让桌面快捷方式真正呈现出现代精品桌面软件应有的水准。
