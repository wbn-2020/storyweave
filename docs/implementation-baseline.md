# 工程起点与本地正文链路

日期：2026-11-05。阶段状态见 [开发进度](../DEVELOPMENT_PROGRESS.md)。本文描述当前批次的实现边界，运行与打包结果另行记录。

## 产品与工程边界

面向个人 Windows 电脑的本地小说工作室。作者选择作品目录，按章编辑与保存。每次正文保存形成可追溯版本；AI、检索与图谱依赖同一作品身份和来源版本。

源码覆盖选择书库、作品与卷章管理、正文编辑和版本保存，以及历史浏览、定稿、文本导入导出和部分故障恢复界面。上述范围已完成静态复核；书内知识、模型、检索与完整恢复包继续按进度文档实施。

| 位置 | 责任 |
|---|---|
| `src/contracts/` | 类型、输入限制、正文结构和错误语义 |
| `src/desktop/main/` | 窗口、原生目录对话框、IPC 来源检查、业务进程与关闭协调 |
| `src/desktop/preload/` | 向界面暴露有限的 `StudioApi` |
| `src/desktop/service/` | 校验后执行本地领域命令 |
| `src/infrastructure/storage/` | SQLite、事务、版本、作品边界与 outbox |
| `src/infrastructure/text/` | 严格文本解码、保留原文的分章、正文交换格式 |
| `src/renderer/` | React 工作室、章节编辑、保存状态与草稿保护 |

界面不持有数据库或任意磁盘路径访问权限；本批次不读取模型凭据。书库通过原生目录对话框选定，应用初始无已选目录，每次启动重新选择。

## 一次保存的具体流程

以“打开第一章，修改两个段落”为例：

1. 界面载入该章的正文 JSON、段落 ID 和当前 revision。
2. 用户输入产生草稿；输入法组合结束后才安排自动保存。手动保存、切章、切书和关闭使用同一串行保存入口。
3. 命令携带作品、章节、预期 revision 和正文。主进程检查页面来源，业务进程校验结构，存储层再检查当前版本。
4. 正文 JSON、纯文本、内容 hash、新 revision、章节指针、作品修订号和 outbox 在书内同一事务中提交。
5. 成功回执才推进界面中的已保存版本。保存期间的新输入仍标为待保存，不用旧回执替换编辑器。
6. 超时视为结果未确认，通过请求回执查询恢复已完成结果；版本冲突保留草稿，不覆盖已有新稿。

outbox 登记正文、作品资料、目录、章节资料和定稿变更，后续 D4 接入任务执行和增量维护。它不是已经整理好的记忆。

## 本地数据布局

```text
作者选择的本地目录/
  studio.sqlite
  books/
    <bookId>/
      book.sqlite
      sources/
        <sourceId>.original
```

工作室数据库保存作品目录；每书数据库保存正文、版本和修订事件。目录标题与时间是缓存，书内元数据是依据。当前只打开一部作品的连接；工作室连接持有独占锁，另一实例不能接管同一书库。实际锁行为、恢复和原生驱动兼容尚未运行验证。

数据库带 application ID 与 schema version。当前结构版本为 v2；未知数据库及早期 v1 格式拒绝写入，尚未实现迁移工具。新建或导入失败会保留已创建资产；当前书库 `books/` 中结构有效的未登记作品可以扫描、预览并明确重新登记。未知、损坏或超限资产只报告跳过，不擅自修改。

正文支持段落、1–3 级标题、分场线、换行、加粗与斜体。段落身份使用 UUID；未知节点、重复身份、非法版本或跨作品章节请求拒绝保存。容量保护上限为每库 1,000 部作品、每书 1,000 卷和 20,000 章、单章 1,000,000 UTF-16 字符和 20,000 块；这些是输入边界，不是容量实测结论。

## 作者版本、目录与恢复

作品与章节资料、卷章重排和定稿使用作品修订号作条件检查；正文保存与历史恢复使用章节当前版本作条件检查。目录的全书章序固定为未分卷、卷顺序、卷内章顺序，建章与转卷后同步重排章号。归档作品可以阅读和导出，继续编辑需要明确解除归档。

历史列表每页最多 50 个摘要，按递增版本序号向前翻页；正文按选中的单个版本读取。恢复旧稿始终新建一个版本，记录恢复来源，保留恢复前正文。作者定稿记录独立指针；之后修改或恢复只推进工作稿，原定稿仍可阅读并按“仅定稿”范围导出。

正文保存冲突或服务故障时，主进程可独立将当前单章草稿、来源身份与纯文本另存为 JSON 文件。此文件不是完整作品恢复包，当前尚无草稿 JSON 自动回导入口。作者另存后明确选择重新读取，才会替换窗口草稿；若期间继续编辑，旧副本不能作为放弃新稿的依据。

本地服务仅在原进程已经退出时重建。恢复进程重开书库确定失败可重试；结果未知则继续核对原回执，不重复写入。数据库彻底损坏、运行中的服务长时间无响应、应用整个进程崩溃后的未保存内容，以及 v1 格式迁移仍有后续恢复工作。

## 文本导入与导出

导入只读取作者在原生对话框选择的 TXT／Markdown 文件；编码选项为 UTF-8、UTF-16LE、UTF-16BE 和 GB18030。不能严格解码时拒绝导入；实际可用编码取决于打包运行时，当前尚未执行验证。预览会提示编码标记与换行规范化。自动分章保留原始标题行、卷首文字和空白；Markdown 当前按字面文字导入，并在预览中说明。

预览 token 绑定书库与解析结果，最多保留一个会话、有效期 30 分钟；调整编码或分章会生成新 token。每次确认先消费 token，再保存全新的作品及原始文件副本，避免重复确认重复建书。输入保护为 32 MiB 原始文件、800 万 UTF-16 字符和 20 万段落；单章与章节数继续遵守正文上限。超限时保留源文件并说明调整方式，不截断正文。

导出固定当前作品修订号，在一个读事务内逐章读取当前工作稿或各章最近定稿。UTF-8 TXT／Markdown 导出始终保留章间空行；作者选择是否额外加入章节标题，已含标题的导入稿可能需要关闭此项。Markdown 保留支持的基本排版，但文本交换不承诺与原始文件逐字节相同，也不携带完整历史和知识资料。

导出及草稿副本采用 `wx` 创建新文件并同步写出；同名文件不覆盖，失败产生的空文件或部分文件保留并说明路径。文件路径只由原生对话框产生，界面不能调用任意路径读写。

## 工程配置与依赖

直接依赖固定在根 `package.json`。本次只读检查 npm 版本与 peerDependencies，并查看 Electron 官方发行记录：Electron 45.2.2 内嵌 Node 24.22.2，因此工程与 Node 类型按 24 系列选择。Tiptap 各核心包同为 3.32.2，React 为 19.3.1，better-sqlite3 为 13.0.3。

electron-vite 输出 main、utility service、preload 和 renderer。主进程与 preload 采用 CommonJS；preload 必须是沙盒可加载的单 bundle，utility service 输出 `out/main/service.js`。better-sqlite3 保留为外部原生依赖，需匹配 Electron ABI。

当前尚未安装依赖，也未生成 lockfile；固定直接版本不等于已锁定传递依赖或已证明构建兼容。首次获准安装时需要固定包管理器版本、生成并审查锁文件，核对实际 SQLite 内核版本，再处理 Electron 原生模块重建。
